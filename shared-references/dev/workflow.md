# PLAN.md 駆動の開発ワークフロー

1枚の計画書（PLAN.md）を唯一の正本にし、利用者は要望を書き足すだけ、AI エージェントはそれをステップに割り当てて実装・確認・記録・版の更新・commit・push までを毎回同じ型で回す。会話の文脈が要約で失われても、PLAN.md と git の履歴から再開できる。
背景: knowledge-base の `[[PLAN.md駆動のAI開発]]`。

パスの表記: dotfiles はローカルでは `~/Github/dotfiles`、クラウドでは `~/dotfiles`。以下 `<dotfiles>` と書く。テンプレートは `<dotfiles>/shared-references/dev/templates/`。

---

## A. 立ち上げ（新しいプロジェクト）

1. **knowledge-base を調べる**（下の「C. knowledge-base の使い方」）。関係する MOC・distill・atomic note を読み、利用者の環境・好み・過去の失敗を把握する。
2. **目的と対象範囲を利用者と合意する**。似た機能の標準アプリ（参照アプリ）があるかを確認する。
3. **技術を選ぶ**（`stack-selection.md`）。コアは Rust を既定とし、フロントエンドを用途と環境から選ぶ。迷ったら S0 で計測して決める。
4. **リポジトリを作る**: `~/Github/<project>` を作り、`gh repo create ikotera/<project> --private --source . --push` 等で GitHub と同期する（公開するかは利用者に確認）。
5. **テンプレートを置く**:

   | テンプレート | 置き先 | 置き換えるもの |
   |---|---|---|
   | `PLAN.md` | `PLAN.md` | `<project>`、日付、参照アプリ、前提知識 |
   | `AGENTS.md` | `AGENTS.md` | `<project>`、ビルド・テストのコマンド |
   | `CLAUDE.md` | `CLAUDE.md` | なし（`@AGENTS.md` の1行） |
   | `Cargo.toml` | `Cargo.toml` | クレート名（Rust の場合） |
   | `gitignore` | `.gitignore` | 必要に応じて追記 |
   | `scripts/bump_version.sh` | `scripts/bump_version.sh` | なし |
   | `scripts/bundle.sh`・`scripts/make_icon.swift` | `scripts/` | アプリ名・バンドル ID・GUI のクレート名（macOS アプリの場合。アプリ化の段階で置けばよい） |

6. **PLAN.md の §1〜§6 を書き、§7.1 を空欄のまま利用者に渡す**。この時点では実装ステップ（§8）を設計しない。
7. 利用者が §7.1 に要望を書いたら、§7.3 に1行1要望で転記し、仕様と要望から §8 のステップを設計する。S0 は「土台のコストの計測と技術の確定」、S1〜S2 は「コアと安全策（GUI 無し）」を基本とする。
8. 未決事項（§9）を質問にまとめて利用者に聞く。回答を「決定済み」に移してから着手する。
9. 初版を commit・push する（版は 0.1.0）。

## B. 1回分の開発（ステップの実装）

利用者が要望を書き足して「実装してください」と言ったとき、またはチャットで依頼を受けたときの流れ。

1. **差分を読む**: `git diff PLAN.md`（または直近のコミットとの差分）で新しい要望を確認する。チャットでの依頼も §7.3 に転記する（備考に「チャットでの依頼を転記」）。要望の原文は書き換えない。ID が重複していたら振り直し、備考に元の番号を残す。
2. **既存のコードを調べる**: すでに実装済みの要望なら、そのことを §7.3 の備考に書き、報告で伝える。
3. **割り当てる**: 要望を §8.2 のステップに割り当て、状態を「計画済」にする。要望の例と実装が食い違いそうな所、決めきれない所は §9 に Q として書き、必要なら着手前に聞く。
4. **実装する**: コアから先に作り、単体テストを書く。GUI は参照アプリに合わせる。
5. **確かめる**:
   - 単体テスト・clippy（`cargo test`、`cargo clippy --all-targets`）。GUI のクレートも `-p` を付けてビルドする。
   - 画面の自動操作（macOS: `[[macOS GUIアプリの自動操作テスト]]`）で、要望どおりに動くか、参照アプリと見た目が揃っているかを見る。
   - 性能に関わる変更なら、§11 の項目を計測して追記する。上限を超えたら報告する。
6. **PLAN.md を更新する**: §7.3 の状態とステップ、§8.2 のステップ行（【完了】と次の版）、§8 のステップごとの詳細の節（画面・操作・制限・推測の明記）、関係する過去の節への追記、§10 の版の履歴、§11 の計測値、§12 の気づきの台帳。
7. **版を上げて commit する**（ステップ完了時。`versioning.md`）: 実装の変更を `git add` してから `scripts/bump_version.sh minor "S<n>: <要約>（R-xxx〜R-yyy）"` を実行する。版の更新・PLAN.md・実装が1つの commit（`v<版>: S<n>: …`）にまとまり、タグ `v<版>` が付く。
8. **push する**: `git push origin main --follow-tags`（タグも送る）。
9. **報告する**（下の書式）。
10. **知識の循環**: 台帳が溜まっていれば distill する（下の「D」）。

### 報告の書式

```text
版: v0.4.0 → v0.5.0（S5: ショートカット変更モード、名前変更）
- 実装したこと（要望 ID ごとに1行）
- 確かめたこと（テスト・画面確認・計測値）
- 制限・推測・利用者に確認したいこと
- push 先: ikotera/<project> の main（タグ v0.5.0）
```

### ステップの途中で中断するとき

- 途中までの変更も commit・push してよい（版は上げない）。PLAN §8.2 のステップ行に「作業中」と、残っている作業を書いておく。

## C. knowledge-base の使い方

- 場所: ローカルは `~/Github/knowledge-base`、クラウドは GitHub の `ikotera/knowledge-base`（private。クラウドのセッションに付けていないと読めない。読めないときはその旨を報告して進める）。
- 読む順番:
  1. `02_MOC/` で関係するトピックの MOC を探す（例: `Rust製macOSアプリ開発`、`Rust学習`、`macOS`、`Appleプラットフォーム開発`）。
  2. MOC から atomic note（`03_Atomic-notes/`）を必要な分だけ読む。
  3. 似たプロジェクトの distill（`01_Distills/`）で、利用者がどこでつまずいたか、何を好んだかを確認する。
- 全文検索: `grep -rl "<キーワード>" 01_Distills 02_MOC 03_Atomic-notes`。
- 使ったノートは PLAN §1.4「前提知識」に `[[ノート名]]` で書く。
- knowledge-base は読むだけにし、書き込みは「D」の手順でだけ行う。

## D. 知識の循環（要約される前に distill する）

会話が要約（compaction）されると、細かい気づきが失われる。要約の時期は予測できないので、**気づいた時点で PLAN.md に書き留め、まとめて distill する**2段構えにする。

1. **台帳に書く（毎回）**: 次のどれかに当たったら、その場で PLAN §12 に1行書く（commit に含める）。
   - ドキュメントに無く、ソースを読んで初めて分かったこと（フレームワークの挙動など）
   - 原因を突き止めるのに時間がかかった不具合と、その原因・対処
   - 計測で分かった数値（予想と違ったもの）
   - 他のプロジェクトでも使える設計の型・手順・スクリプト
   - 利用者の好み・環境についての新しい発見
2. **distill する（まとめて）**: 次のどれかで、台帳の「候補」を knowledge-base へ atomic note として distill する。
   - 台帳の「候補」が3件以上たまった
   - 版の minor 以上を上げた（ステップの完了）
   - 会話が長くなった（目安: 大きなステップを2つ以上終えた、大量のログやファイルを読んだ）
   - 利用者がセッションの終了を告げた
3. 手順は skill `session-distill-to-knowledge-base`（Claude Code）、または `<dotfiles>/shared-references/distill-atomic-workflow.md` に従う。プロジェクトごとの distill を1枚作り、atomic note を作り、関係する MOC へ登録する。
4. distill したら、台帳の状態を `distill 済み → [[ノート名]]` に変える。プロジェクト固有でしかない事項は「対象外」にする。

## E. PLAN.md が大きくなったら

- 目安として 60 KB を超えたら、完了したステップの詳細の節（§8.x）を `docs/steps/S<n>.md` に移し、PLAN.md には要約1行とリンクを残す。§7.3（要望一覧）・§8.2（ステップ一覧）・§9（未決事項）・§10（版の履歴）は PLAN.md から外さない。
