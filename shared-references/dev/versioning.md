# 版の管理

## 方針

- 版は SemVer（Semantic Versioning、意味に基づく版番号）の `MAJOR.MINOR.PATCH` で表す。
- **利用者に届けるまとまりごとに1回上げる**。まとまりとは「PLAN のステップ1つ」または「ステップの外でチャットで頼まれた修正1件」。ステップの途中の commit では上げない。
- 上げたら、**その都度、報告の先頭で利用者に伝える**（`版: v0.4.0 → v0.5.0（S5: …）`）。
- **メインの画面に常に版を表示する**（ステータスバー、サイドバーの下端、タイトルバーのどれか。参照アプリの見た目を崩さない所）。「について」画面だけでは足りない。

## どの桁を上げるか

| 変更 | 1.0.0 より前 | 1.0.0 以降 |
|---|---|---|
| 機能を足したステップ | MINOR（0.4.0 → 0.5.0） | MINOR（1.2.0 → 1.3.0） |
| 不具合の修正だけのステップ・チャットでの修正 | PATCH（0.5.0 → 0.5.1） | PATCH（1.3.0 → 1.3.1） |
| 保存形式・設定ファイル・ファイル名の書式など、以前のデータと互換が無くなる変更 | MINOR（1.0.0 前は互換を保証しない） | MAJOR（1.3.1 → 2.0.0）。移行の手順を PLAN に書く |
| 日常で使い始める（アプリ化してインストールする等） | 1.0.0 にする | ― |

例（file-classifier）: S12 のタグの仕様の変更（旧形式のタグを認めなくした）は、1.0.0 以降なら MAJOR にあたる。

## 版の正本と表示

- Rust: ワークスペースの `Cargo.toml` の `[workspace.package] version` を唯一の正本にし、各クレートは `version.workspace = true` で受ける。
- GUI では `env!("CARGO_PKG_VERSION")` で埋め込む。CLI は clap の `#[command(version)]` で `--version` に出す。
- アプリにする場合は `Info.plist` の `CFBundleShortVersionString` も同じ版にする（テンプレートの `bundle.sh` は `Cargo.toml` から読む）。
- Rust 以外のフロントエンド（SwiftUI 等）を使う場合も、版は1か所（Rust ワークスペースか、設定ファイル1つ）に置き、ビルド時に流し込む。

## 手順

```bash
scripts/bump_version.sh minor   # または patch / major
```

`bump_version.sh` は、`Cargo.toml` の版を書き換え、`Cargo.lock` を更新し、`Cargo.toml`・`Cargo.lock`・`PLAN.md` の変更をまとめて `v<版>: <要約>` で commit し、注釈付きタグ `v<版>` を付ける。PLAN.md の更新（§8.2・§10）を済ませてから実行する。push は `git push origin main --follow-tags`。

## なぜステップ単位か

- 利用者が受け取って確かめる単位がステップなので、版とステップを1対1にすると「どの版で何が入ったか」が PLAN §10 だけで分かる。
- commit ごとに上げると、途中の状態にも版が付き、版の数が増えるだけで情報が増えない。
- 一方で、ステップの外の修正にも版を付けるので、「ソースが変わったのに版が同じ」状態で利用者に渡ることは無い。
