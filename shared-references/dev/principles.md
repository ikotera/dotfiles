# 開発原則

個人用のアプリ・ツールを AI エージェントと作るときの共通原則。各原則は「何で確かめるか」とセットで運用し、結果は PLAN.md に記録する。
出自: file-classifier（Rust＋GPUI 製のファイラー、S0〜v1.0.0、2026-10-11〜13）。背景の知識は knowledge-base の MOC `[[Rust製macOSアプリ開発]]` にある。

## 1. 省資源（メモリと計算資源を占有しない）

| 規則 | 確かめ方 |
|---|---|
| 最初のステップ（S0）で、土台（フレームワーク・ランタイム）だけのコストを計測し、それを下限として PLAN §11 に記録する | 空のウィンドウや最小構成の起動で計測 |
| PLAN §11.1 に性能の上限を数値で決める（例: 無操作時の CPU ほぼ0、phys_footprint 100 MB 以下） | ステップごとに再計測して §11.2 に追記 |
| 常駐する索引・データベース・ファイル監視・毎フレームの再描画を安易に持たない。必要になったら、計測してから範囲を絞って足し、判断を §9（未決事項）に残す | 足す前後の計測値 |
| 重い処理（サムネイル・走査・圧縮等）は、表示中の分だけ・必要になった時だけ行い、使い終わったら解放する | 繰り返し操作でメモリが増え続けないこと |
| 外部ツールで済むものは、ライブラリを抱え込まずに子プロセスで呼ぶことも検討する（バイナリと常駐メモリを小さく保つ） | バイナリサイズ、常駐メモリ |

計測の道具（macOS）:

- メモリ: `footprint <pid>` の phys_footprint を主に使う（RSS は共有ページを含むため参考値。`[[physical footprintとRSS]]`）。
- 無操作時の CPU: `ps -o time= -p <pid>` を一定時間（10秒）の前後で取り、増分を見る。
- 単発のコマンド: `/usr/bin/time -l`（最大メモリと CPU 時間）。
- 起動と初回描画: 環境変数（例 `<APP>_MEASURE=1`）で、起動から最初の描画までの時間を標準エラーに出す仕組みを最初から入れておく。

## 2. 心地よさ（速く、引っかからない）

| 規則 | 確かめ方 |
|---|---|
| UI のスレッドで、ファイルの入出力・外部コマンド・重い計算をしない。バックグラウンドで行い、結果だけを UI に渡す | 処理中もスクロール・キー操作が効くこと |
| 長い処理には進み具合（百分率）と中止（ボタン・Esc・⌘.）を付ける。中止したら元に戻る順番で処理を組む（`[[キャンセル可能なバッチ処理]]`） | 実データでの中止の確認 |
| キー連打を取りこぼさない。主な操作は全てキーボードで完結する | 例: 下キーを400回連続で送って、カーソルが400行目に届くか |
| 起動直後からキー操作・メニューが効く（初期フォーカス。`[[GPUIの初期フォーカス]]`） | 起動直後に ⌘, などを送る |
| 一覧は数万件でも引っかからない（仮想スクロール、必要な分だけ描画） | 1万件のフォルダでの操作と計測 |
| 似た標準アプリがある場合は、その操作感（キー割り当て・クリック・ダブルクリック・右クリック・ドラッグ）に合わせる（`macos-look-and-feel.md`） | 参照アプリとの比較表 |

## 3. 堅牢性と安全性

| 規則 | 確かめ方 |
|---|---|
| コア（GUI・OS 非依存）を分け、GUI より先に単体テストで固める。GUI 無しで動かせる CLI を用意し、確認と一括操作に使う | `cargo test`（GUI を含まない既定のビルド対象） |
| データを壊しうる処理（リネーム・移動・削除・上書き）は「計画 → プレビュー → 記録（ジャーナル）→ 実行 → 取り消し」の順に作る。削除はゴミ箱へ移す | 取り消しのテスト、失敗分の再試行 |
| 書き込む前に検証する（名前の衝突、長さの上限、使えない文字、権限）。検証で落ちたものは書き込まない | 境界値の単体テスト |
| `unsafe` は原則禁止（`unsafe_code = "deny"`）。OS の API を呼ぶ所だけ、モジュール単位で許可し理由を書く | clippy、lints |
| `unwrap` は警告にし、失敗しうる所は型（`Result`・独自エラー型）で扱う | clippy |
| 秘密情報（鍵・トークン）をリポジトリに置かない。設定は `~/.config/<project>/` 等に置く | `git diff` の確認 |
| 外部の入力（ファイル名・外部コマンドの出力・ネットワーク）は信用しない前提で解釈する | 異常な入力の単体テスト |

## 4. 技術選定: Rust コア＋用途に応じたフロントエンド

- **コアは Rust を既定にする**。省資源・速度・メモリ安全を同時に満たしやすく、コアを GUI から分ければ、フロントエンドを後から替えたり増やしたりできる。
- **フロントエンドは、用途と動作環境に応じて毎回比較して決める**。候補と選び方は `stack-selection.md`。迷ったら S0 で候補ごとに空のウィンドウを作って計測し、決めてから先へ進む。
- 選んだ案と選ばなかった案、その理由を PLAN §1.3 に残す。
- 小さな使い捨ての処理（数十行のスクリプト、一度きりの変換）まで Rust にする必要はない。シェルや Python で済むものは済ませる。

## 5. 見た目と操作感

- 似た機能の標準アプリ（例: ファイル管理なら Finder）がある場合は、それを**参照アプリ**として PLAN の冒頭に書き、見た目・配置・用語・キー割り当て・メニューの並びまで全面的に合わせる。独自の工夫は、参照アプリに無い機能に限る。
- 具体的なチェック項目は `macos-look-and-feel.md`。

## 6. 版の管理と表示

- ステップを完了するたびに版を上げ、報告の先頭で利用者に伝える。メインの画面に常に版を表示する。詳細は `versioning.md`。

## 7. 知識の循環

- 着手前に knowledge-base を調べ、利用者の目指す方向・環境・過去の課題を把握する。
- 他のプロジェクトにも役立つ気づきは、PLAN §12 の台帳に書き留め、会話が要約（compaction）される前に knowledge-base へ atomic note として distill する。手順は `workflow.md` の「知識の循環」。
