# 定量研究の規律（探索と確認）

バックテスト・統計的な検証を伴うプロジェクト（投資戦略、予測モデルなど）で使う。`principles.md` §3 から参照する。

## 1. 探索と確認を分ける

| 区分 | 探索モード（既定） | 確認モード |
|---|---|---|
| 目的 | 有望な仮説を効率よく見つける | 実際の判断（資金の投入、公開など）をする |
| データ | 封印日より前。何度見てもよい | 封印日以降の前向きデータ、または一度も読み込んでいない対象 |
| 仕様の変更 | 自由 | 不可。git に凍結した仕様を1回だけ評価する |
| 結果の扱い | 「探索」と明記し、判断に使わない | 判断に使う |

- 探索の試行錯誤は歓迎する。厳密な盲検は確認モードにだけ求める。
- 盲検性を守るのは「仕様を決めた時点で答えを知らなかったこと」。結果を見た人が書いた仕様を、別のセッションや別のモデルに渡して実行させても、確認にはならない。別のモデルは、独立した再実装（コードの誤りの発見）と仕様の監査には使える。

## 2. 再発を防ぐ規則

1. **封印を機械で守る**: 封印日以降のデータは、ローダーが既定で除外する。解除には理由付きの明示的な指定を要し、解除は試行台帳に自動で記録する。人やエージェントの注意に頼らない。
2. **委任時に封印を伝える**: サブエージェントへの指示に、封印日と「それ以降を読み込まない」を書く。全期間の実行を頼むときは探索であると明記する。
3. **陽性対照を先に**: 論文の効果を扱うときは、まず論文と同じ窓・定義・期間で再現し、論文の値と並べて確認してから、自分の変更を1つずつ加える。再現できないデータやパイプラインで、新しい仮説を判定しない。
4. **探索でも台帳を残す**: 試した仕様を1行ずつ追記する。確認モードで多重検定の補正（DSR など）をするときの試行回数に使う。
5. **見た後の仕様は確認してから判断する**: 探索で生まれた仕様は、凍結して封印日以降のデータで評価するまで採否を決めない。
6. **閲覧してしまったら封印日を前に進める**: 封印した期間を見てしまった場合は、その期間を探索用に繰り入れ、新しい封印日を設けて PLAN に記録する。
